# 第六章 框架开发实践

## 原教程讲了什么

介绍 LangChain、AutoGen 等主流 Agent 框架的使用方法，展示如何用框架快速搭建 Agent 应用。

## 本 Harness 如何映射

本 harness 本身就是一个 Agent 框架的**最小完整实现**。对比学习 LangChain 使用的价值在于：理解框架为你隐藏了什么，以及为什么本 harness 做出了不同的取舍。

核心模块对应：

| LangChain 概念 | Harness 对应 |
|---|---|
| Chain / LCEL | `runAgentLoop` — 固定的 AsyncGenerator pipeline |
| Tool / StructuredTool | `src/tools/tool.ts` — Tool 接口 + ToolRegistry |
| AgentExecutor | `AgentRuntime.run()` — 封装 runLoop 为 AsyncGenerator |
| Memory / ConversationBufferMemory | `SessionStore` + `ContextBuilder` |
| Callbacks | `AgentEvent` + `TraceWriter` + `TrajectoryRecorder` |
| OutputParser | tool_call delta 累积 + JSON parse |
| PromptTemplate | `agentInput()` + `gatherContextSources()` |

## 原理解析：为什么本 Harness 不依赖 LangChain

LangChain 是一个庞大且高度抽象的框架。本 harness 刻意不依赖它，原因：

1. **抽象层太多**：LangChain 的 `RunnableLambda` → `RunnableSequence` → `AgentExecutor` 调用链很深，debug 时需要穿透 5-6 层抽象
2. **Prompt 缓存不友好**：LangChain 的 message 构造往往产生不同结构的 message 列表，降低 Anthropic/DeepSeek 的 prompt cache 命中率
3. **Streaming 粒度不一致**：不同 LangChain 组件对 streaming 的支持程度不同，容易出现"某一段不 stream"的惊喜
4. **重**：依赖体积大，不适合"理解每一行代码"的学习目标

本 harness 的选择是：**约 4400 行 TypeScript，0 个 Agent 框架依赖**。每个模块都可以在一个文件中读完。

### 框架设计的核心权衡

hello-agents 教程教你"用框架"，本章教你"理解框架做了哪些取舍"。以 Tool 系统为例：

**LangChain 的方式**：
```python
from langchain.tools import tool

@tool
def read_file(path: str) -> str:
    """Read a file"""
    ...
```

装饰器自动生成 schema、自动序列化、自动注册。但你想知道"tool call 的 arguments 怎么 validate 的？"需要追踪多层代码。

**Harness 的方式**：
```typescript
const read_file: Tool = {
  name: "read_file",
  risk: "read",
  description: "Read a UTF-8 text file inside HARNESS_WORKSPACE.",
  inputSchema: {
    type: "object",
    properties: {
      path: { type: "string" },
      maxChars: { type: "number" },
    },
    required: ["path"],
    additionalProperties: false,
  },
  run(input, ctx) {
    const maxChars = typeof input.maxChars === "number" ? Math.floor(input.maxChars) : 20_000;
    const result = ctx.workspace.files.readText(String(input.path), maxChars);
    return { ok: true, content: result.content, data: result, truncated: result.truncated };
  },
};
```

一切都显式：schema 就是 JSON Schema 字面量，validate 在 `ToolRunner.validateJsonSchema()` 中是 30 行显式类型检查，执行在 `run()` 中是同步/异步/生成器三种支持的统一处理。

## 操作指南

### 在自己的工具中对比框架设计

试着在 harness 中添加一个新工具（比如 `count_lines`），然后对比如果用 LangChain 的 `@tool` 装饰器实现，你会失去哪些控制：

1. 无法指定 risk level（LangChain 无安全分级）
2. 无法控制 streaming vs non-streaming 返回（LangChain 抽象不区分）
3. 无法精确控制 tool result 的 model 可见性（bounded observation truncation）
4. 无法集成 approval gate

### 参考 LangChain 但不照搬

本 harness 借鉴了 LangChain 的以下思想，但用自己的方式实现：

| 借鉴的思想 | Harness 实现 |
|---|---|
| Tool 抽象 | `Tool` 接口 — 更薄，更显式 |
| Agent 类型 | `createAgent(name)` — 6 种 mode，通过 prompt 合约而非子类实现 |
| Memory | `MemoryStore` + `SessionStore` — 分离持久记忆和会话历史 |
| Output parsing | 直接 JSON.parse + 错误返回，不做 Pydantic 验证 |
| Callbacks | AsyncGenerator events — 不用 callback 地狱 |

## 超越原教程

| hello-agents 第六章 | 本 harness |

| 学习使用 LangChain | 理解 LangChain 的设计决策，然后自己实现一个更薄的版本 |

| 关注"怎么用" | 关注"为什么这样设计" |

当你将来使用 LangChain 时，你会知道它内部的 AgentExecutor 在做什么：它也在做 tool call 增量累积、tool result 转 message、context window 管理——只是被 6 层抽象包裹。

## 关键文件

| 文件 | 作用 |
|---|---|
| `src/tools/tool.ts` | Tool 接口 — 整个工具系统的基石 |
| `src/tools/registry.ts` | ToolRegistry — 注册/查找/导出 |
| `src/tools/runner.ts` | ToolRunner — 解析/验证/权限/执行/序列化 |
| `src/tools/permissions.ts` | 权限门控 |
| `src/runtime/loop.ts` | 相当于 LangChain AgentExecutor 的核心 loop |

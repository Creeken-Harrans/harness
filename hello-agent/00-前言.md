# 前言：从 Hello-Agents 到工程级 Agent Runtime

## 一、什么是 Agent Harness

### 1.1 先定义术语

在进入正文之前，先厘清本文档中反复出现的几个概念。

**Agent（智能体）**：一个能够**感知环境 → 推理决策 → 使用工具执行动作 → 观察反馈 → 继续推理**的自主系统。这里的"推理"由一个语言模型（LLM）完成，"工具"是 Agent 可以调用的外部能力（读写文件、执行 shell、搜索记忆等），"环境"是 Agent 所操作的工作区（文件系统、终端、持久记忆）。

**Agent Runtime（智能体运行时）**：不是一段脚本、不是一个函数调用，而是一个**持续运行的事件循环**。它管理 Agent 的完整生命周期：接收用户输入 → 构建上下文 → 调用模型 → 解析工具调用 → 执行工具 → 收集观察 → 再次调用模型 → ... → 最终回答。Runtime 还负责可观测性（trace / trajectory）、安全边界（approval / path policy）、资源限制（timeout / max steps / context budget）。

**Harness（线束/测试架）**：工程术语，原指电气系统中用于组织和管理线缆的装置。在软件工程中引申为一个为被测试或被运行的组件提供**所有必要基础设施**的框架。本项目的 "harness" 含义是：它不是一个"应用"，而是一个为 DeepSeek Agent 提供了模型连接、工具调度、上下文管理、记忆存储、安全策略、可观测性和评估能力的**完整运行底座**。你在这个底座之上可以运行任意 Agent、测试任意工具、收集任意轨迹。

**Agent Harness = Agent Runtime + Tool System + Context Engineering + Memory + Safety + Observability + Eval**

### 1.2 一个具体例子

当你对着本 harness 的 REPL 输入 "列出当前目录的文件" 时，实际发生的是：

```
你输入文字
  → ContextBuilder 从 SOUL.md、AGENTS.md、memory、session history、workspace summary 中
    收集(gather)→ 选择(select)→ 组织(structure)出一个 messages 数组
  → DeepSeekClient 把 messages + 18 个 tool definitions 发往 DeepSeek API（stream=true）
  → SSE 字节流被 parseDeepSeekSse() 解析为 ModelStreamEvent 序列
  → content_delta → 终端实时打印
  → tool_call_delta 逐字段累积 → 拼出 tool_calls[0]: { name: "list_dir", arguments: { path: "." } }
  → ToolRunner 接收 tool call → 查 ToolRegistry → 校验 JSON Schema → 检查 permission policy
    → workspace path policy 验证路径未逃逸 → 执行 fs.readdirSync → 返回 ToolResult
  → ToolResult 被 redact + truncate 后作为 tool message 追加到 messages
  → messages 再次发给 DeepSeek → 模型基于观察结果生成最终回答
  → 同时: TraceWriter 把每一步写入 data/traces/{runId}.jsonl
  → 同时: TrajectoryRecorder 把聚合信息写入 data/trajectories/{runId}.json
```

这一整条链路，从输入到输出到 trace，全在本 harness 的约 4400 行 TypeScript 中显式实现。没有任何隐式行为、没有任何第三方 Agent 框架依赖。

## 二、为什么不用 Python 照搬教程

hello-agents（《从零开始构建智能体》）是一本优秀的入门教程，以 Python 为主要教学语言，从 LLM 基础到 Agentic RL 逐层展开。但教学代码和工程代码之间存在一条关键的鸿沟。理解这条鸿沟，是阅读本文档的第一个收获。

### 2.1 同步调用 vs 全链路 Streaming

**教程做法**：
```python
response = llm.chat(messages)      # 阻塞等待
print(response.content)            # 拿到完整结果后再打印
if response.tool_calls:
    result = execute_tool(...)     # 阻塞等待
    messages.append(result)
    response = llm.chat(messages)  # 再次阻塞等待
```

**工程要求**：用户的终端应该在模型还在"思考"时就逐字显示输出；工具执行时应该实时显示 stdout/stderr；trace 应该同步写入而非事后补记。

本 harness 的解决方案：**全链路 AsyncGenerator**。从 SSE 解析 → ModelStreamEvent → AgentEvent → CLI renderer / TraceWriter / TrajectoryRecorder，全部是一个生成器链上的消费者。没有回调、没有 Promise.race、没有缓冲后批量输出。

### 2.2 隐式拼接 vs 显式 Context Engineering

**教程做法**：对话历史、system prompt、工具输出通常用字符串拼接或简单的 list append 混在一起。

**工程要求**：context window 是有限资源（token 预算）。你需要知道每个 source 消耗了多少 token、哪些被 drop 了、为什么被 drop。system prompt（SOUL.md）、工作流指令（AGENTS.md）、记忆检索结果、会话历史、workspace 摘要——这些来源需要有明确的优先级和选择策略。

本 harness 的解决方案：**Gather → Select → Structure → Compress → Budget** 五阶段显式管道。每一步都有结构化的输入输出，`/context` 命令可以查看上一次构建的完整报告。

### 2.3 无安全边界 vs 多层防御

**教程做法**：`open("file.txt")` 直接读，`subprocess.run(cmd)` 直接执行。

**工程要求**：
- 文件操作不能逃逸 workspace
- 敏感路径（.env、.ssh、密钥文件）默认拒绝
- shell 命令需要审批门控
- 危险的 shell 模式（rm -rf /、mkfs、dd of=/dev/）硬编码拒绝
- API key 不能写入 trace / trajectory / 错误日志

本 harness 的解决方案：**WorkspacePathPolicy**（路径逃逸检测 + 敏感路径拒绝）+ **ApprovalPolicy**（safe/read 免审批、write/shell/network 审批门控、dangerous 默认拒绝）+ **Terminal 硬拒绝模式** + **三层 redaction**（trace / trajectory / tool-result）。

### 2.4 不可观测 vs 结构化 Trace & Eval

**教程做法**：出问题时 `print(...)` 调试。

**工程要求**：
- 每次 run 产生结构化事件流（jsonl trace），可以事后回放
- 聚合的 trajectory（json）可以直接用于 RL 训练或评估
- 有自动化的 eval suite，每次改动后 `npm run eval` 验证不回归

本 harness 的解决方案：**TraceWriter**（逐事件 jsonl）+ **TrajectoryRecorder**（聚合 json）+ **Eval Runner**（6 个基础 case，rule-based judge）。

## 三、核心概念速览

以下概念贯穿本文档的所有章节。在进入具体章节之前先建立它们的准确定义。

### 3.1 AsyncGenerator — 不仅是语法，是架构选择

`AsyncGenerator<Yield, Return>` 是 TypeScript 中表达"异步值序列"的类型。在本 harness 中，它是整个 runtime 的脊椎：

```typescript
// src/runtime/loop.ts
export async function* runAgentLoop(
  deps: RuntimeDeps,
  input: string,
): AsyncGenerator<AgentEvent, AgentResult> {
  // yield* 产出事件（流中间的值）
  yield* emit({ type: "llm_delta", runId, delta: "你" });
  yield* emit({ type: "llm_delta", runId, delta: "好" });
  // ...
  // return 最终结果（流结束后的值）
  return { runId, finalText: "你好！", steps: 1, stoppedReason: "final" };
}
```

选择 AsyncGenerator 而不是 EventEmitter 或回调的核心原因：

1. **单一控制流**：调用方用 `for await (const event of stream)` 消费，不需要注册/注销 listener
2. **天然背压**：如果 CLI 渲染慢了，生成器自动暂停等待
3. **可组合**：`yield*` 可以委托给另一个生成器，形成清晰的管道
4. **明确的终止**：`return` 给出最终值（AgentResult），区分"流中间的值"和"流结束后的值"

### 3.2 AgentEvent — 统一的事件语言

`src/runtime/events.ts` 中定义的 `AgentEvent` 是一个 discriminated union，涵盖了 Agent 运行时中可能发生的所有事件：

```
user_message      → 用户输入
llm_delta         → 模型逐字输出（最终展示给用户的内容）
llm_reasoning_delta → 模型思考过程（DeepSeek reasoning_content，未必展示）
assistant_message → 模型一次完整输出（可能包含 tool_calls 数组）
tool_call_start   → 工具开始执行
tool_stdout       → 工具实时 stdout 输出
tool_stderr       → 工具实时 stderr 输出
tool_progress     → 工具进度报告
tool_call_end     → 工具执行结束（含 ok / result / shellResult）
trace             → 元信息
error             → 错误
done              → 一次 run 结束（含 AgentResult）
```

**关键设计**：`AgentEvent` 是单一事实来源（single source of truth）。CLI renderer 消费它来显示、TraceWriter 消费它来记录、TrajectoryRecorder 消费它来聚合。三者之间互不知晓，只依赖同一个事件流。

### 3.3 Tool Calling — 模型表达"我需要调用工具"的协议

DeepSeek（以及 OpenAI 兼容的 API）的 tool calling 协议：

1. **你告诉模型有哪些工具可用**：通过 `tools` 数组，每个工具包含 name、description、parameters（JSON Schema）
2. **模型输出 tool_calls**：在 streaming 模式下，tool call 是逐字段 delta 到达的（id → function.name → function.arguments 逐段）
3. **你执行工具并返回结果**：将 ToolResult 序列化为 `role: "tool"` 的 message，追加到对话历史
4. **模型基于结果继续推理**：下一次调用时模型看到 tool message，做出下一步决策

本 harness 在步骤 2（delta 累积，`accumulateToolCall()`）和步骤 3（ToolRunner 统一执行+序列化+脱敏）上做了大量工程处理，是区别于教程 demo 的关键所在。

### 3.4 Context Window — 有限资源的显式管理

每次调用 DeepSeek API 时，`messages` 数组中的所有内容都消耗 token。Token 预算是有限的（默认 24000，由 `HARNESS_CONTEXT_BUDGET` 控制）。

Context Engineering 要回答的问题：
- 哪些内容进入 context？（Gather）
- 按什么优先级？（priority 字段）
- 超出预算时谁被裁掉？（Select，mandatory source 保护）
- 如何组织为模型可读格式？（Structure）
- 太长的内容如何截断？（Compress）

这不是"把什么都丢给模型就行"——context 质量直接影响 Agent 表现。

### 3.5 Memory 的三个层次

本 harness 区分三个层次的"记忆"，它们有不同的生命周期和访问方式：

| 层次 | 存储 | 生命周期 | 访问方式 |
|---|---|---|---|
| **Session（会话）** | `data/sessions/*.json` | 单次 REPL 会话 | ContextBuilder 自动注入最近历史 |
| **Memory（持久）** | `data/memory.json` | 跨会话 | `memory_add` / `memory_search` 工具 + ContextBuilder 自动注入相关条目 |
| **Notes（任务状态）** | `data/notes/*.md` | 跨会话 | 通过 `note_read` / `todo_list` 等工具按需访问，**不自动注入 context** |

Notes 不自动注入 context 是一个有意识的设计选择：任务笔记可能很长，且并非每次推理都需要全部回顾，按需查阅更高效。

### 3.6 Trace vs Trajectory

| | Trace（jsonl） | Trajectory（json） |
|---|---|---|
| **粒度** | 逐事件 | 聚合摘要 |
| **格式** | 每行一个 JSON 事件 | 单个 JSON 对象 |
| **用途** | Debug、回放、审计 | RL 训练、评估分析、指标统计 |
| **大小** | 大（完整事件流） | 小（摘要+结构化字段） |
| **路径** | `data/traces/{runId}.jsonl` | `data/trajectories/{runId}.json` |

两者都经过 `security/secrets.ts` 的 `redactValue()` 脱敏：API key、`sk-*` token、`Authorization: Bearer` header、PEM 私钥等敏感字段在写入前被替换为 `[REDACTED]`。

## 四、设计哲学

这五条原则贯穿本 harness 的所有模块，理解它们能帮你更快地读懂源码。

### 4.1 DeepSeek-first，不做通用 Provider

本 harness 的模型客户端只有 `DeepSeekClient`。不引入 OpenAI / Anthropic / Qwen provider 抽象。原因：

- DeepSeek 有独特能力（reasoning_content、thinking mode）无法被最小公分母抽象覆盖
- 避免抽象泄漏（leaky abstraction）
- 4400 行的项目无需为"可能用到的其他 provider"提前付出复杂度

但消息格式和 tool schema 是 DeepSeek/OpenAI 兼容的，因为 DeepSeek 支持这一协议形状。这是**利用兼容性**，而非**构建多 provider 框架**。

### 4.2 Prompt-Contract Agent Mode，而非硬编码状态机

6 种 Agent mode（simple / react / plan / reflection / coding / research）共享同一个 `runAgentLoop`。它们之间的差异不在于代码分支，而在于注入给模型的不同 system prompt 指令。

这建立在一个洞察之上：LLM 的核心能力之一是**遵循自然语言指令**。如果你能通过自然语言让模型表现出 ReAct 行为或 Plan-Execute 行为，就不需要在代码中维护多个状态机——让模型自身管理其内部状态。

### 4.3 Registry 模式，而非 Switch-Case

工具（Tool）的注册、查找、执行全部通过 `ToolRegistry` + `ToolRunner` 完成。添加新工具只需要实现 `Tool` 接口并注册，不修改任何调度代码。

### 4.4 安全内建，而非事后附加

Path policy、approval gate、redaction、hard deny patterns 不是"插件"——它们内嵌在 `ToolRunner.runWithEvents()`、`WorkspaceFileStore`、`Terminal.runStream()`、`TraceWriter.write()` 的执行路径中，无法绕过。

### 4.5 可观测性内建，而非事后日志

TraceWriter 和 TrajectoryRecorder 在 `runAgentLoop` 的第一行创建，从第一个事件开始记录。不需要"开启 debug 模式"——每次 run 默认就有完整的事件轨迹。

## 五、本文档的阅读方式

### 5.1 章节结构

本文档按照 [hello-agents](https://github.com/datawhalechina/hello-agents) 教程的章节编排，每章对应一个独立的 `.md` 文件。每章的标准结构：

1. **原教程讲了什么** — 一句话概括该章在 hello-agents 中的内容
2. **本 Harness 如何映射** — 该章涉及的概念在本 harness 中由哪些模块实现
3. **原理解析** — 深入讲解设计原理、为什么这样做、和原教程方法的本质差异
4. **操作指南** — 具体的 bash 命令、代码示例、验证步骤
5. **超越原教程** — 对比表格，列出 harness 提供了哪些原教程没有的工程能力
6. **关键文件** — 该章涉及的核心源文件索引

### 5.2 推荐阅读路径

- **如果你刚开始接触 Agent 工程**：按顺序从头读到尾（01→16），每章的"操作指南"部分都实际运行一遍
- **如果你已经读过 hello-agents，想快速找到某个主题的对应实现**：直接跳到对应章节，看"本 Harness 如何映射"和"关键文件"
- **如果你只有 2 小时，想理解整个 harness 的骨架**：读 07-构建你的Agent框架.md，然后按其中列出的 11 个核心文件顺序阅读源码

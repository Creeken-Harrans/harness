# 第六章 框架开发实践

## 原教程讲了什么

hello-agents 第六章围绕 LangChain 和 AutoGen 两个主流 Agent 框架展开，系统讲解了：

- **LangChain 核心概念**：Chain/LCEL（LangChain Expression Language）——将 Prompt、LLM 调用、Output Parser 串联为可执行管道；Tool/StructuredTool——通过 `@tool` 装饰器将 Python 函数自动转为 LLM 可调用的工具；AgentExecutor——LangChain 的 Agent 运行时，负责 thought→action→observation 循环
- **AutoGen 多 Agent 模式**：通过 `ConversableAgent` 定义不同角色的 Agent，`GroupChat` 管理多 Agent 对话，展示 Agent 间协作的编程模式
- **快速搭建**：用几十行代码搭建一个能调用工具的 Agent 应用

**不足**：第一，LangChain 的抽象层过深——`RunnableLambda` → `RunnableSequence` → `AgentExecutor` 的调用链需要穿透 5-6 层才能理解实际发生的事情，debug tool call 增量累积这类底层问题几乎不可能。第二，不同 LangChain 组件对 streaming 的支持程度不一致，容易出现"某一段不 stream，整段阻塞"的行为，这对用户体验是致命的。第三，OutputParser 的 Pydantic 验证层在 tool call JSON parse 失败时给的错误信息不透明。第四，依赖体积大——LangChain 全家桶安装体积超过 500MB，不适合"理解每一行代码"的学习目标。

**本 harness 的改进**：约 4400 行 TypeScript，**0 个 Agent 框架依赖**。以 Tool 系统为例——LangChain 用 `@tool` 装饰器自动生成 schema、自动序列化、自动注册，但你无法知道 argument 如何 validate；harness 用 30 行显式的 `validateJsonSchema()` 做类型检查，schema 就是 JSON Schema 字面量。每个模块都可以在一个文件中从头读到尾（最大文件约 220 行），理解成本可控。LangChain 的 Chain/AgentExecutor/Callbacks 在 harness 中分别对应 `runAgentLoop`（固定的 AsyncGenerator pipeline）、`AgentRuntime.run()`（封装 loop 为 AsyncGenerator）、`AgentEvent` + `TraceWriter`（结构化事件而非 callback 地狱）。

## 本 Harness 如何映射

本 harness 本身就是一个 Agent 框架的**最小完整实现**（约 4400 行，0 个 Agent 框架依赖）。对比 LangChain 学习时，理解框架为你隐藏了什么、以及 harness 为什么做出不同取舍：

| LangChain 概念 | Harness 对应 | 设计差异 |
|---|---|---|
| Chain / LCEL | `runAgentLoop` — 固定的 AsyncGenerator pipeline | 不用 Runnable 链式组合，单一生成器函数，控制流一目了然 |
| Tool / StructuredTool | `src/tools/tool.ts` — `Tool` 接口 + `ToolRegistry` | 不用 `@tool` 装饰器，显式 JSON Schema + 手动 validate，30 行可读 |
| AgentExecutor | `AgentRuntime.run()` — 封装 runLoop | 不用 AgentExecutor 的复杂状态机，直接 AsyncGenerator |
| Memory | `SessionStore` + `MemoryStore` | 不用 ConversationBufferMemory 等抽象，JSON 文件直接读写 |
| Callbacks | `AgentEvent` 联合类型 + `TraceWriter` + `TrajectoryRecorder` | 不用 callback 函数注册，事件通过 AsyncGenerator yield 给消费者 |
| OutputParser | `accumulateToolCall()` — tool_call delta 累积 + `JSON.parse` | 不用 Pydantic 验证，直接 JSON.parse + 错误路径返回 |
| PromptTemplate | `agentInput()` + `gatherContextSources()` | 不用 Jinja2 模板，纯字符串拼接 + 优先级注入 |

核心差异：LangChain 的 `@tool` 装饰器自动生成 schema、自动序列化、自动注册——方便但黑盒。Harness 的每个 Tool 是显式的 JSON Schema 字面量 + `validateJsonSchema()`（30 行显式检查）+ `run()` 函数。你想知道 argument 如何验证？读那 30 行就够了。

## 原理解析：为什么本 Harness 不依赖 LangChain

LangChain 是一个庞大且高度抽象的框架。本 harness 刻意不依赖它，原因：

1. **抽象层太多**：LangChain 的 `RunnableLambda` → `RunnableSequence` → `AgentExecutor` 调用链很深，debug 时需要穿透 5-6 层抽象
2. **Prompt 缓存不友好**：LangChain 的 message 构造往往产生不同结构的 message 列表，降低 Anthropic/DeepSeek 的 prompt cache 命中率
3. **Streaming 粒度不一致**：不同 LangChain 组件对 streaming 的支持程度不同，容易出现"某一段不 stream"的惊喜
4. **重**：依赖体积大，不适合"理解每一行代码"的学习目标

本 harness 的选择是：**约 4400 行 TypeScript，0 个 Agent 框架依赖**。每个模块都可以在一个文件中读完。

### 框架设计的核心权衡

hello-agents 教程教你"用框架"，本章教你"理解框架做了哪些取舍"。以 Tool 系统为例：

**LangChain 的方式**：
```python
from langchain.tools import tool

@tool
def read_file(path: str) -> str:
    """Read a file"""
    ...
```

装饰器自动生成 schema、自动序列化、自动注册。但你想知道"tool call 的 arguments 怎么 validate 的？"需要追踪多层代码。

**Harness 的方式**：
```typescript
const read_file: Tool = {
  name: "read_file",
  risk: "read",
  description: "Read a UTF-8 text file inside HARNESS_WORKSPACE.",
  inputSchema: {
    type: "object",
    properties: {
      path: { type: "string" },
      maxChars: { type: "number" },
    },
    required: ["path"],
    additionalProperties: false,
  },
  run(input, ctx) {
    const maxChars = typeof input.maxChars === "number" ? Math.floor(input.maxChars) : 20_000;
    const result = ctx.workspace.files.readText(String(input.path), maxChars);
    return { ok: true, content: result.content, data: result, truncated: result.truncated };
  },
};
```

一切都显式：schema 就是 JSON Schema 字面量，validate 在 `ToolRunner.validateJsonSchema()` 中是 30 行显式类型检查，执行在 `run()` 中是同步/异步/生成器三种支持的统一处理。

## 操作指南

### 在自己的工具中对比框架设计

试着在 harness 中添加一个新工具（比如 `count_lines`），然后对比如果用 LangChain 的 `@tool` 装饰器实现，你会失去哪些控制：

1. 无法指定 risk level（LangChain 无安全分级）
2. 无法控制 streaming vs non-streaming 返回（LangChain 抽象不区分）
3. 无法精确控制 tool result 的 model 可见性（bounded observation truncation）
4. 无法集成 approval gate

### 参考 LangChain 但不照搬

本 harness 借鉴了 LangChain 的以下思想，但用自己的方式实现：

| 借鉴的思想 | Harness 实现 |
|---|---|
| Tool 抽象 | `Tool` 接口 — 更薄，更显式 |
| Agent 类型 | `createAgent(name)` — 6 种 mode，通过 prompt 合约而非子类实现 |
| Memory | `MemoryStore` + `SessionStore` — 分离持久记忆和会话历史 |
| Output parsing | 直接 JSON.parse + 错误返回，不做 Pydantic 验证 |
| Callbacks | AsyncGenerator events — 不用 callback 地狱 |

当你将来使用 LangChain 时，你会知道它内部的 AgentExecutor 在做什么：它也在做 tool call 增量累积、tool result 转 message、context window 管理——只是被 6 层抽象包裹。

## 关键文件

| 文件 | 作用 |
|---|---|
| `src/tools/tool.ts` | Tool 接口 — 整个工具系统的基石 |
| `src/tools/registry.ts` | ToolRegistry — 注册/查找/导出 |
| `src/tools/runner.ts` | ToolRunner — 解析/验证/权限/执行/序列化 |

| `src/runtime/loop.ts` | 相当于 LangChain AgentExecutor 的核心 loop |

# 第九章 上下文工程

## 原教程讲了什么

hello-agents 第九章引入了 Context Engineering 这一 Agent 工程的核心概念，系统讲解了：

- **Context Engineering 定义**：上下文工程不是简单的"写 prompt"，而是系统性地管理每次 LLM 调用时注入的所有信息——system prompt、对话历史、记忆检索结果、工具执行结果、项目规则等
- **上下文窗口管理**：LLM 的 context window 有 token 上限（如 128K），需要合理分配空间给不同优先级的上下文来源
- **上下文组织策略**：system message 放最前面（行为指令），user/assistant messages 保持时间顺序（对话流），tool results 紧跟在对应 tool call 之后

**不足**：第一，原教程停留在**概念层面**——讲解了 Context Engineering 是什么，但没有给出可运行的上下文构建管道。读者学完后知道"应该管理 context window"，但不知道如何实现自动的 budget 计算和裁剪。第二，手工管理 context window——需要开发者自己估算 token 数、自己决定哪些内容保留哪些丢弃，没有优先级系统和自动选择机制。第三，不同上下文来源的重要性不同（system prompt 是强制性的，一段旧对话可能是可丢弃的），但原教程没有区分优先级和强制性。第四，上下文构建过程对开发者不透明——无法事后查看某次 LLM 调用注入了哪些 source、哪些被丢弃了。

**本 harness 的改进**：实现了完整的 **gather → select → structure → compress → budget** 五阶段上下文管道。**Gather** 收集所有上下文来源并标记优先级（system-base 1000、SOUL.md 950、AGENTS.md 900、memory-relevant 700、session messages 500+ 按新旧递增、workspace-index 350）。**Select** 按优先级排序后填充 budget，system/soul/agents 为强制 source（即使超出 budget 也包含），被丢弃的 source 记录在 `ContextBuildReport` 中。**Structure** 将 systemSources 合并为一条带 `[context:kind:id]` 标签的 system message，后接 transcript。**Compress** 提供 rule-based 截断（头尾保留，中间截断）。全流程通过 `/context` 命令可视化——可以看到每次构建的 budget 使用量、selectedSources 列表、droppedSources 及丢弃原因。

## 本 Harness 如何映射

Context 系统是一个完整的五阶段管道，每个阶段由独立模块负责：

```
gatherContextSources()          → 收集所有可能的上下文来源（system / soul / agents / memory / session / workspace-index）
  → selectContextSources()      → 按优先级排序，填充 context budget，强制保留 system/soul/agents
    → structureDeepSeekMessages() → 将 systemSources 合并为 system message + 拼接 transcript
      → compress (truncateText / summarizeLongObservation) → 对超长内容做头尾保留截断
        → budget (approximateTokens / createBudget) → 估算 token 数，记录 used/dropped
```

核心文件：
- `src/context/builder.ts` — `ContextBuilder.build()`：入口，调用 gather → select → structure，返回 `ChatMessage[]`
- `src/context/gather.ts` — `gatherContextSources()`：从 `SessionStore`、`MemoryStore`、`SOUL.md`、`AGENTS.md`、workspace index 收集所有 context source，每个 source 标记 `kind` / `priority` / `estimatedTokens`
- `src/context/select.ts` — `selectContextSources()`：按 priority 降序排列，填充 budget；system/soul/agents 为 mandatory（即使超出 budget 也包含），被丢弃的 source 记录到 `ContextBuildReport`
- `src/context/structure.ts` — `structureDeepSeekMessages()`：将 systemSources 合并为一条 system message（带 `[context:kind:id]` 标签前缀），后接 transcript
- `src/context/compress.ts` — `truncateText()`（头 65% + 尾 35% 保留）+ `summarizeLongObservation()`（tool result 截断至 4000 字符）
- `src/context/budget.ts` — `approximateTokens()`（char/4 估算）+ `createBudget()`（maxTokens / usedTokens / dropped 列表）
- `src/context.ts` — `ContextManager` 兼容包装，对外暴露 `build()` + `getReport()`（供 `/context` 命令使用）

## 原理解析：Gather → Select → Structure 管道

### Step 1: Gather（收集）

`gatherContextSources()` 收集所有可能进入 context 的内容，标记优先级：

```
优先级 1000: system-base (基础 system prompt)
优先级  950: SOUL.md (项目级灵魂指令)
优先级  900: AGENTS.md (工作流指令)
优先级  700: memory-relevant (相关记忆)
优先级  500+: session messages (对话历史，越新优先级越高)
优先级  350: workspace-index (项目结构摘要)
```

每个 source 都有：`id`、`kind`、`priority`、`content`、`tokens`(估算)、`metadata`。

### Step 2: Select（选择）

`selectContextSources()` 按优先级排序，从高到低填充 context budget：

```typescript
for (const source of sorted) {
  const tokens = sourceTokens(source);
  const mandatory = source.kind === "system" || source.kind === "soul" || source.kind === "agents";
  if (!mandatory && budget.usedTokens + tokens > budget.maxTokens) {
    budget.dropped.push({ source: source.id, reason: "context budget exceeded", ... });
    continue;
  }
  budget.usedTokens += tokens;
  // session sources → transcript (user/assistant messages)
  // other sources  → systemSources (合并为 system message)
}
```

关键设计：
- **system/soul/agents 是强制的**：即使超出 budget 也会包含（因为它们定义 Agent 的基本行为）
- **session messages 按时间排序**：保留对话的正确顺序
- **被 drop 的 source 有记录**：存入 `ContextBuildReport`，可通过 `/context` 查看

### Step 3: Structure（结构）

`structureDeepSeekMessages()` 将 systemSources 合并为一条 system message，然后拼接 transcript：

```typescript
function structureDeepSeekMessages(selected: SelectedContext): ChatMessage[] {
  const systemContent = selected.systemSources
    .sort((a, b) => b.priority - a.priority)
    .map(source => "[context:" + source.kind + ":" + source.id + "]\n" + source.content)
    .join("\n\n");
  return [
    { role: "system", content: systemContent },
    ...selected.transcript,
  ];
}
```

注意每个 source 被标记了 `[context:kind:id]` 前缀——这在 debug 时非常有用，可以快速识别某段 system message 来自哪个 source。

### Step 4: Compress（压缩）

`compress.ts` 提供两种基础压缩：

1. **`truncateText(text, maxChars)`** — 头尾保留，中间截断
   - head: 65% maxChars
   - tail: 35% maxChars - 80 (留给 `...[truncated N chars]...` 标记)

2. **`summarizeLongObservation(text, maxChars=4000)`** — 对 tool observation 做压缩

这些是当前的基础实现。未来可以用 DeepSeek summarizer 替代规则截断（见 ROADMAP.md）。

## 操作指南

### 查看 Context 构建报告

```bash
npm run dev

# 进行一次对话后查看
/context
```

输出示例：
```json
{
  "sessionId": "default",
  "messageCount": 4,
  "approximateHistoryTokens": 1250,
  "memoryCount": 3,
  "maxContextTokens": 24000,
  "lastContext": {
    "budget": { "maxTokens": 24000, "usedTokens": 8234 },
    "selectedSources": [
      { "id": "system-base", "kind": "system", "estimatedTokens": 125 },
      { "id": "soul", "kind": "soul", "estimatedTokens": 68 },
      { "id": "memory-relevant", "kind": "memory", "estimatedTokens": 340 },
      ...
    ],
    "droppedSources": [
      { "source": "workspace-index", "reason": "context budget exceeded", "estimatedTokens": 500 }
    ],
    "recentSessionCount": 4,
    "memoryHits": 3,
    "workspaceIndexStatus": "dropped"
  }
}
```

### 调整 Context Budget

```bash
# 减小 budget 观察 drop 行为
HARNESS_CONTEXT_BUDGET=4000 npm run dev

# 进行对话后 /context 查看
# 你会发现更多 source 被 dropped
```

### 定制 System Prompt

编辑 `SOUL.md` 会直接影响每次 LLM 调用：

```bash
cat > SOUL.md << 'EOF'
# SOUL.md
你是一个 Linux 系统管理助手。
回答时默认使用中文。
对于 shell 命令，先解释用途，再请求执行。
永远不要在未确认的情况下执行 rm、chmod、chown。
EOF

npm run dev
# 现在 Agent 的行为会遵循 SOUL.md 中的规则
```

### 验证 Context 注入

在 `runAgentLoop` 中，`deps.context.build()` 返回的 messages 直接传给 `client.chatStream()`。你可以通过 trace 查看实际发送给模型的 system message：

```bash
# 从 trace 中提取 model_request 事件（包含 messageCount 和 toolCount）
cat data/traces/<runId>.jsonl | python3 -c "
import sys, json
for line in sys.stdin:
    e = json.loads(line)
    if e['type'] == 'model_request':
        print(f'step={e[\"step\"]} messages={e[\"messageCount\"]} tools={e[\"toolCount\"]}')
"
```

## 超越原教程

| hello-agents 第九章 | 本 harness |
|---|---|
| Context Engineering 概念 | 完整的 gather→select→structure→compress→budget 管道 |
| 手工管理 context window | 自动 budget 管理 + dropped source 可见 |
| 无优先级系统 | 基于 priority 的选择机制 + mandatory source 保护 |
| 无压缩策略 | rule-based truncation（头尾保留） |
| 无可见性 | `/context` 命令 + ContextBuildReport |
